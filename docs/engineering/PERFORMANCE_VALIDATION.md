# Sensveil 启动与管理页性能修复记录

日期：2026-10-13。本次修复应用目录图标处理与界面重复刷新造成的启动、操作卡顿。完整自动化测试和安装运行通过，修复后本机采样未再出现原有图标编解码热点；结果仅覆盖本文记录的启动与管理页交互。

## 修复前证据与根因

用户报告打开应用缓慢、所有操作有明显延迟，并观察到 CPU 约 800%。当时实际运行的是 10 月 12 日安装的产品，不能将该二进制等同于当前仓库 HEAD。协调者实测 `ps` 显示 CPU 1023.9%、RSS 4,260,032 KiB（约 4.06 GiB）。CPU 百分比按多个核心累计，可能超过 100%。

对该进程执行 `/usr/bin/sample`，持续 5 秒，启动阶段记录到的 392 个主线程样本全部位于 `SensveilController.init → refreshApplications → ApplicationCatalog` 图标处理链路：283 个涉及 TIFF，109 个涉及 PNG。启动后的另一轮采样显示主线程持续忙于 SwiftUI 图像处理。

原实现同步扫描应用目录、读取 plist、为全部应用生成图标。修改 `NSImage.size` 只改变逻辑尺寸，不能移除源图的高分辨率表示；随后 TIFF/PNG 编解码仍处理大图。管理页一次构造全部应用行，每次权限轮询和未变化的保护状态又会触发视图刷新，放大图像处理成本。协调器启动时还因同步 startup 回调和显式 reconcile 执行两轮初始化。

修复前的回归测试实际失败：

- 合成图标输出仍为 1024 × 1024、PNG 176,265 字节，超过测试要求的 64 × 64 和 16,384 字节；控制器初始化及同步目录刷新测试耗时约 2.9 秒。
- 连续两次权限刷新在权限未变化时，各发布 2 次辅助功能和录屏状态更新，预期均为 0。
- 同步 startup 造成 2 次 reconcile，预期为 1；未变化的窗口/权限事件仍发布状态更新。

## 修复范围

应用图标现在绘制到新的 64 × 64 位图后编码为 PNG，并按应用 URL 缓存；目录遍历和 plist 解析移出主线程。AppKit 图像绘制保留在主线程，每处理 8 个图标让出执行权。控制器异步刷新目录并合并重复请求，管理页应用列表改为 `LazyVStack`。

权限状态与保护状态只在实际变化时通知界面；时段判定变化仍正常通知。启动只执行一轮初始 reconcile，未发送 startup 回调的运行时仍会初始化。没有调整模糊路线、权限用途或隐私判定，也没有引入窗口快照缓存。

## 修复后本机观察

首次安装运行保留 2 个配置应用，CPU 一次观察为 0.7%，采样期间另一观察为 6.7%；RSS 约 207–224 MiB。5 秒采样记录 453 个主线程样本，其中 431 个等待 Mach 消息（约 95.1%），未出现原有 TIFF/PNG 热点。

管理页搜索、刷新应用列表、展开保护设置均完成。对应工具调用耗时约 0.49、0.47、0.63 秒，包含 UI 自动化操作和读取界面结果，**不是精确的输入响应时延**，也不是失焦到安全模糊的 PRD 预算测量。

## 剩余边界与 Task 8

图标缓存以 URL 为键，同一路径替换应用图标后可能需要重启才更新；后台目录发现任务的取消尚未完全传播。窗口跟踪仍有同步 AX 调用及回调后重复快照读取，本次采样没有将其定位为主要热点，暂未修改；其他窗口数量、目标应用响应状态和系统生命周期下的 CPU/RSS 仍需测量。

本次性能修复不放行视觉集成。材料 Gate 仍为 **UNMEASURED**，所需 3 名独立可读性评估者当前为 0；Task 8 尚未开始，须先满足[计划中的前置门槛](../superpowers/plans/2026-10-13-protection-effects-and-schedule.md)和 [POC_RESULTS](POC_RESULTS.md) 的层级、输入、强度验证。
